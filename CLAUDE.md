# asset-risk

Take a CSV of `(id, lat, lon)`, identify each point's building with `geolocate`, assess its physical
climate risk with `physrisk`, and show the portfolio in a web dashboard.

The plan is epic #1. So far `app/engine` and `app/front` exist; the rest arrives with issues #10–#11.

## Stack
- Python >= 3.11, DuckDB >= 2.0, `physrisk-lib` (pinned exactly: its output has no stability promise)
- `geolocate`: git submodule at `vendor/geolocate`, imported directly
- FastAPI for the API, TypeScript (Vite + React) for the front end
- Terraform or OpenTofu (`infra/`) owns the run settings and writes a git-ignored `.asset-risk.json`
- Docker (`docker/`): one image and a compose stack

## Architecture
```
app/front            upload a CSV, follow progress, view results
  → app/engine/api.py        FastAPI: start a background run, serve results
  → app/engine/pipeline.py   ingest → geolocate → classify → assess → store
      geolocation.py   the only importer of vendor/geolocate/src
      classify.py      Overture class/subtype + region → valid physrisk (type, location)
      assess.py        physrisk get_asset_impact per (scenario, year)
      store.py, sql/   one DuckDB file per run, SQL views for the results
script/              ad-hoc CLIs
```
`app/` is on the path through pytest (`pythonpath` in `pyproject.toml`), so the package is `engine`.

## Contracts
- **`.asset-risk.json`** (written by `infra/main.tf`, read by `app/engine/settings.py`): keys
  `scenarios`, `years`, `default_building_type`, `physrisk_batch_size`, `geolocate_workers`,
  `geolocate_batch_size`, `max_portfolio_rows`, `max_upload_mb`, `data_dir`, `api_port`,
  `geolocate_config`. Change both sides together, including the allowed values, which are checked
  in both places so a hand-edited file fails too. Relative paths are relative to the repo root.
- **`.geolocate.json`**: written to `vendor/geolocate/` by geolocate's own stack, which `infra/` calls
  as a module. `$GEOLOCATE_CONFIG` overrides the path in `.asset-risk.json`, which is only valid on
  the machine that ran `apply`.

- **geolocate's output CSV** (written in `app/engine/geolocation.py`, loaded by
  `app/engine/sql/load_assets.sql`): the engine reads this documented interface, not geolocate's
  internals. A submodule bump must keep `test/engine/test_store.py` passing.
- **Run database** (`<data_dir>/runs/<uuid>/run.duckdb`, `app/engine/sql/schema.sql`): `assets` has one
  row per input row in input order, keyed on `row_num`, because invalid rows can have no id. Folder
  names are generated; the uploaded file's name is only ever stored as a label.

- **Classification columns on `assets`** (`app/engine/sql/classify.sql`): `physrisk_type`,
  `physrisk_location`, `type_source` (`class | subtype | assumed`), `location_fallback`, `assessable`
  and `exclusion_reason` (`invalid | off_land | no_curve`). Only `assessable` rows go to physrisk.
- **`app/engine/sql/building_type_map.csv`**: `class` beats `subtype`. A blank `physrisk_type` means
  the value says nothing about use. Audit it with `script/overture_values.py`.
- **`app/engine/data/countries.geojson`** (generated by `script/build_regions.py`, committed): never
  hand-edit it.

- **Results** (`app/engine/sql/schema.sql`, `views.sql`): `impacts` and `scores` are keyed on `row_num`,
  `scenario` and `year`, and the historical baseline has year NULL. The API and dashboard read the
  `v_*` views. Portfolio figures are equal-weighted means of assets that have results.

- **API** (`app/engine/api.py`, `schemas.py`): `app/front/openapi.json` is generated by
  `script/export_openapi.py` and committed, and a test checks it's current. Errors are always
  `{"detail": "readable message"}`. Assets are addressed by `row_num`, because an invalid row can
  have no id and an id can contain any character. Results are 409 until a run is `completed`.

- **Front-end types** (`app/front/src/api/schema.d.ts`): generated from `app/front/openapi.json` with
  `npm run gen:api`. After an API change, run `/sync-generated`. Never hand-edit it.
- **Front-end tests** live in `test/front`, outside the package. `vite.config.ts` and `tsconfig.json`
  resolve their dependencies from `app/front`.
- TypeScript stays on 5.x: `openapi-typescript` 7 doesn't work with TypeScript 7.

- **Dashboard colours**: `lib/hazards.ts` fixes each hazard's colour, in the order validated with the
  dataviz palette validator, against the surfaces in `styles.css`. Re-validate before changing them.

## Rules
- Never edit `vendor/`. To change geolocate, change its own repo and bump the submodule. A bump also
  moves the Overture release, because geolocate's `infra/` pins it.
- geolocate exposes top-level modules named `config`, `db`, `match` and `geolocate`. Don't add
  top-level modules with those names, and don't put `app/engine` itself on the path.
- No `__init__.py` under `test/`: `test/engine` as a package would shadow the `engine` package, and
  `test` would shadow the standard library's. Test file names must therefore be unique.
- Unit tests never touch the network. Live tests are marked `s3`, `live` or `e2e` and are excluded by
  default.
- physrisk accepts unknown types and locations without error and returns a fallback result. Only send
  values checked against its embedded vulnerability config.
- Never treat a low score as proof of low risk: a mid-ocean point scores `Very low` for flood, and
  scenarios can silently drop hazards. See `docs/physrisk_demo.ipynb`, section 8.
- Most Overture buildings have no class or subtype (97% in a sample), so `default_building_type`
  often decides the type. Keep `type_source` visible wherever results are shown.
- With DuckDB's `spatial`, run `SET geometry_always_xy = true`, then always pass (lon, lat).
- Hazards differ by scenario: `ssp245` has no fire or hail, `ssp126` only those two, and `ssp370`
  nothing. Only compare totals across scenarios using `mean_shared_aal` or `shared_aal`.
- A failed physrisk batch means no results, never zero loss: it's recorded in `assess_failures`.
- One worker process only: the run queue lives in memory. Calls into physrisk go through the lock in
  `assess.py`, because the API and the background run share it.
- In the dashboard, compare scenarios only on shared hazards, and history only on the same hazards as
  the selected scenario. Keep "No model" and "No data" visibly different from a low score.
- Pass values into SQL as parameters (`?`), never via string formatting.
- Never commit `.asset-risk.json`, `.geolocate.json`, `*.tfstate*` or `*.tfvars`: they may contain
  credentials.

## Commands
- Install: `git submodule update --init && uv venv .venv && uv pip install -p .venv -r requirements-dev.txt`
  and `npm --prefix app/front ci`
- Front end: `npm --prefix app/front run dev` (proxies `/api` to port 8000) · `run build` · `test` ·
  `run typecheck`. `script/serve.py` serves the built `dist/` once it exists. Map tiles default to
  OpenFreeMap; override with `VITE_MAP_STYLE_LIGHT` and `VITE_MAP_STYLE_DARK` at build time.
- Lint: `.venv/bin/ruff check --fix .` · Format: `.venv/bin/ruff format .`
- Serve: `.venv/bin/python script/serve.py` · API docs at `/docs`
- Tests: `.venv/bin/pytest` (no network) · Live: `.venv/bin/pytest -m s3`, `-m live` or `-m e2e`
- Infra: `terraform -chdir=infra init && terraform -chdir=infra apply` (or `tofu`)
